## 2. 十八条硬约束

这些约束的共同特点：**违反它们会让代码更短更简单**，因此实施时有强烈的本能去改掉。每条都附了"为什么"和"怎么验证没被违反"。

### H1. 索引主键必须是 `(volume_uuid, inode)`，不是路径

- **为什么**：用户在 Finder 里整理一次 Downloads 目录，若以路径为主键，全库要重新解析 + 重新嵌入。
- **验证**：写测试——移动/重命名一个已索引文件，断言解析函数与嵌入函数**均未被调用**，且 `files.path` 已更新。
- **参见**：§8

### H2. 默认不移动、不重命名、不删除任何原始文件

- **为什么**：这是产品第一条不可协商约束（§1）。组织行为全部发生在索引层。
- **验证**：§18.1 阻塞项"未经确认的文件移动/删除/改名 = 0"。集成测试跑完 100 文件后，比对全部源目录的文件清单与哈希，必须与运行前完全一致。
- **参见**：§2.1

### H3. 保全副本是**复制**，不是移动

- **为什么**：微信/QQ 会清理缓存目录。复制失败的最坏结果是多一个待清理的临时文件；移动失败可能丢文件。
- **验证**：注入"复制后校验失败"的故障，断言源文件仍然存在且哈希不变。
- **参见**：§2.5、§11.5

### H4. 跨卷操作永远"先复制 → 校验哈希 → 后删源"，顺序不可颠倒

- **为什么**：中途断电时，这个顺序最坏留下可清理的临时文件；颠倒则丢文件。
- **验证**：在校验步骤注入异常，断言源文件完好、目标残留已清理。
- **参见**：§11.6

### H5. LLM 只返回 `category_id`，绝不返回路径

- **为什么**：让模型自由生成路径 = 主动制造路径穿越攻击面。路径由后端从 `categories.rel_path` 映射。模型返回未知 id 时判为低置信度走人工确认，**不要尝试"修复"它**。
- **验证**：检查 LLM 响应 schema 中不存在任何路径类字段。
- **参见**：§16.1

### H6. 自动发现的来源默认**不启用**

- **为什么**：自动监听用户没同意的目录是隐私问题。§1 约束 4。
- **验证**：§18.1 阻塞项"未经用户启用的目录被监听 = 0"。
- **参见**：§7.4

### H7. chunks / chunks_fts / chunks_vec 三表写入必须在**同一事务**

- **为什么**：这是选 sqlite-vec 而非 LanceDB 的核心理由（§4.3）。三表不同步会产生搜得到但打不开、或向量指向已删除 chunk 的悬挂状态。
- **验证**：在向量写入步骤注入异常，断言 chunks 与 FTS5 均已回滚。
- **参见**：§12.2 ④

### H8. 引用后置校验不是可选项

- **为什么**：§18.2 把"引用正确率 ≥ 0.90""正确拒答率 ≥ 0.80"设为**阻塞**验收项。仅靠 prompt 约束达不到——**prompt 是建议，校验是执行**。
- **必须实现四条**：虚构 `[Cn]` 剔除 → 无引用则重新生成 → 二次失败降级为检索结果列表（不输出自然语言答案）→ 拒答句混入事实则截断。
- **验证**：构造模型输出 `[C9]`（上下文中不存在）的用例，断言被剔除。
- **参见**：§12.4

### H9. `chat.citations` 必须在生成完成**之后**推送

- **为什么**：引用边生成边推，校验失败时已推给用户的引用收不回。
- **验证**：检查 SSE 推送顺序，`chat.citations` 在最后一个 `chat.token` 之后。
- **参见**：§12.4

### H10. 增量更新按片 diff，不整文件重嵌入

- **为什么**：200 页合同改一条条款，重嵌入代价应从 200 页降到 1 片。决定产品在"文件反复编辑"这一真实场景下是否可用。
- **验证**：构造 200 片文档改 1 片，**断言 embed 调用次数为 1**。
- **参见**：§12.5

### H11. 元数据类问题不进 RAG

- **为什么**："上周微信收到的 PDF" 走 SQL 是毫秒级且 100% 准确，走 RAG 又慢又可能答错。
- **验证**：对纯元数据问题断言嵌入函数**未被调用**。
- **参见**：§12.3 ①

### H12. 评测集标注必须**先于** B3 完成

- **为什么**：否则会不自觉地照着已有实现出题，指标失去意义。且 B2 改分片策略会触发全量重建，基线必须在此之前锚定。
- **验证**：M6 是 M7 的前置里程碑。
- **参见**：§18.2、§20

### H13. **[v5]** chunks 挂在 `contents` 上，**不是** `files`

- **为什么**：v4 的 `chunks.file_id` 与"去重复用 chunks"直接冲突——原件删除会级联删掉副本仍在用的向量。三表结构 `files (N) → contents (1) → chunks (N)` 是唯一自洽解。
- **验证**：删原件保副本，chunks 必须存活。
- **参见**：§9.1、§12.1

### H14. **[v5]** 中文检索必须 jieba + trigram 双索引

- **为什么**：FTS5 默认 unicode61 把中文整句当一个 token，`保修`、`验收` 这类双字词**零命中**。这不是优化项，是功能缺失。
- **验证**：阻塞验收项，见 §18.1。
- **参见**：§9.1

### H15. **[v5]** 必须有目录黑名单与规模上限，且**先预扫描再入库**

- **为什么**：`~/Downloads` 里一个 `node_modules` 就是 5 万文件；`.photoslibrary` 是 40 万。没有这道闸，首次扫描直接跑死。
- **验证**：断言黑名单路径未被下钻。
- **参见**：§7.7

### H16. **[v5]** 增量 diff 以 `text_hash` 为主键，**不是** `section_path`

- **为什么**：文档开头插一段就会让所有 section 编号平移，按 path 匹配等于全量重嵌。
- **验证**：200 片改 1 片 → embed 调用次数 == 1。
- **参见**：§12.5

### H17. **[v5]** 流式输出用"草稿 token + finalize"，引用校验**在 finalize 前**

- **为什么**：v4 同时要求"边生成边显示"和"校验后才返回"，二者互斥。已定为草稿可见 + 校验失败则显式 `chat.regenerating` 重来。
- **验证**：校验失败时前端必须能看到重生成提示，而不是静默替换。
- **参见**：§12.4

### H18. **[v5]** 单实例锁 + 分级损坏恢复

- **为什么**：两个实例同时写 SQLite 必损；FTS5 索引损坏时若走全量重嵌，等于把 20 分钟的活干成 3 小时。
- **验证**：注入损坏 FTS5，断言 embed 未被调用。
- **参见**：§9.2

## 3. 已排除的方案（不要绕回去）

附录有完整论证。这里只列结论，**如果你觉得某条应该改，先看附录的理由，再提出来讨论，不要直接改**：

| 不要做 | 已排除的理由（简版） |
|---|---|
| 移动归档模式 | 带来跨卷/断电/重名/撤销回滚一整批复杂度，收益（Finder 里按分类浏览）已用符号链接镜像零风险拿到 |
| 以路径为索引主键 | 见 H1 |
| LanceDB | PyInstaller 打包成本高；且跨库无法与 FTS5 同事务（H7） |
| LLM 生成文件路径 | 见 H5 |
| 用户手动配置监听目录 | 微信接收目录是带 hash 的动态路径，用户根本配不出来 |
| 强制人工确认才入库 | 索引模式下分类无破坏性，卡点没有必要，改为非阻塞的「待确认」队列 |

## 5. 容易混淆的概念

方案里有几组措辞相近但语义不同的概念，**混用会导致实现错误**：

| 概念 A | 概念 B | 区别 |
|---|---|---|
| **保全副本** (preserve) | **可选归档** (relocate) | 保全=复制，原文件留着；归档=移动，删源。前者是主流程，后者是极少用的手动操作 |
| **child chunk** | **parent chunk** | child 用于**检索**（512 token，语义集中）；parent 用于**送模型**（3 个 child 合并，上下文完整）。只有 child 参与嵌入 |
| **missing** | **volume_offline** | missing=文件找不到（可能被移走/删除）；volume_offline=整个卷未挂载。后者不触发重定位，卷回来自动恢复 |
| **category** | **tag** | **book** | category=单选、树形、决定镜像目录位置；tag=多选、扁平；book=虚拟集合，可限定检索范围 |
| **duplicate** | **ignored** | duplicate=哈希与已有文件相同（复用索引）；ignored=用户主动忽略 |

## 6. 需要你自行决定但必须告知的事项

这些方案有意没有写死，实施时你来定，**但定完要明确写进代码注释或 README**：

1. **模型型号与参数**——§16.1 说"实施时现查最新文档确定"。**不要凭记忆硬编码一个模型名**，很可能已过期。查当前可用的模型列表再定，并把选择理由写下来。
2. **嵌入模型**——已定案（0.3.0）：本机 Ollama + bge-m3（1024 维，多语言）。未检测到 Ollama 或未拉模型时全链路降级纯 FTS5 关键词检索；维度变更由 `db/database._init_vec_table` 自动重建向量表并触发回填。此前的 model2vec 静态嵌入（256 维）已移除。
3. **token 分词器**——§12.2 的 512/800 token 用什么算？中英文差异很大。
4. **置信度阈值**——"低置信度进待确认队列"的具体阈值。

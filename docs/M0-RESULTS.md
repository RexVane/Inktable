**日期**：2026-08-11 · **机型**：Apple M1 / 16GB / macOS 25.5.0

M0 的唯一目的：在写任何业务代码之前，确认技术栈能打成一个能跑的 macOS 应用。
方案 §20 定的规则是「冒烟不过不写业务代码」，因为打包是本项目最高风险项。

## 实测发现的两个检索缺陷（方案未覆盖）

这是 M0 的额外收获 —— 两个都会让搜索静默漏结果，且都不是靠读文档能发现的。

### 缺陷 1：2 字词在双索引下双向落空

查「保修」搜不到含"保修期"的文档：

- **jieba 侧**：`jieba.cut` 精确模式把"保修期"切成单个词元，索引里没有"保修"
- **trigram 侧**：只索引 3 字符组，2 字查询词天然不命中

两条路都断了，结果是 0 命中。

**修法**：建索引时用 `jieba.cut_for_search`（全切分），它对"保修期"同时产出
"保修"和"保修期"。查询侧保持精确模式。索引略微变大，换来 2 字词可检索。

### 缺陷 2：带连字符的编号被 FTS5 当语法解析

查 `HT-2024-0023` 报错或返回错误结果 —— FTS5 把 `-` 当作 NOT 运算符。
讽刺的是这类编号检索恰恰是引入 trigram 索引的主要理由。

**修法**：查询串一律用双引号包裹成短语查询，内部双引号转义为两个双引号。
必须在**所有**用户输入进入 MATCH 之前统一处理，不能靠调用方自觉。

两条修正已写入 `services/api/search.py`，8/8 用例通过。

# M2 决策记录：源码类降级为仅元数据

**问题**：启用 `~/Documents` 后入库 1438 个文件，其中 59% 是源码/配置（.json/.js/.py），
它们会被解析正文、分片、嵌入 —— 而这不是产品定位。

**否决的方案：按目录排除**（识别 `code/` `src/` `repos/` 等路径特征）。
实测证明会误杀真文档：`~/Documents/code/ai-file-library/PLAN.md` 和 `HANDOFF.md`
都在代码目录里，但它们恰恰是最该被索引的设计文档。
而且路径启发式本身失效 —— 大量 `main.py`、`__init__.py` 散在 `~/Documents` 下，
根本不在任何"代码目录"里。

**采用的方案：按扩展名降级**。源码/配置进 `CODE_EXTS`，只登记元数据不解析正文。

| | 改前 | 改后 |
|---|---|---|
| 入库文件数 | 2503 | 2503（不变，仍可按文件名搜到） |
| 需解析正文 | 1092 | **128（-88%）** |

**用户损失**：无法全文搜索源码内容。但那本就该用 ripgrep / IDE 全局搜索，
不是文件管理器的职责。

**关键细节**：`.md` **不归入** CODE_EXTS。它既是文档格式又常驻代码库
（README、设计文档），按扩展名归文档类是对的；用路径判断会误杀。

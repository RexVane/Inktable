## 实测发现的两个检索缺陷（方案未覆盖）

这是 M0 的额外收获 —— 两个都会让搜索静默漏结果，且都不是靠读文档能发现的。

### 缺陷 1：2 字词在双索引下双向落空

查「保修」搜不到含"保修期"的文档：

- **jieba 侧**：`jieba.cut` 精确模式把"保修期"切成单个词元，索引里没有"保修"
- **trigram 侧**：只索引 3 字符组，2 字查询词天然不命中

两条路都断了，结果是 0 命中。

**修法**：建索引时用 `jieba.cut_for_search`（全切分），它对"保修期"同时产出
"保修"和"保修期"。查询侧保持精确模式。索引略微变大，换来 2 字词可检索。

### 缺陷 2：带连字符的编号被 FTS5 当语法解析

查 `HT-2024-0023` 报错或返回错误结果 —— FTS5 把 `-` 当作 NOT 运算符。
讽刺的是这类编号检索恰恰是引入 trigram 索引的主要理由。

**修法**：查询串一律用双引号包裹成短语查询，内部双引号转义为两个双引号。
必须在**所有**用户输入进入 MATCH 之前统一处理，不能靠调用方自觉。

两条修正已写入 `services/api/search.py`，8/8 用例通过。

# M2 决策记录：源码类降级为仅元数据

**问题**：启用 `~/Documents` 后入库 1438 个文件，其中 59% 是源码/配置（.json/.js/.py），
它们会被解析正文、分片、嵌入 —— 而这不是产品定位。

**否决的方案：按目录排除**（识别 `code/` `src/` `repos/` 等路径特征）。
实测证明会误杀真文档：`~/Documents/code/ai-file-library/PLAN.md` 和 `HANDOFF.md`
都在代码目录里，但它们恰恰是最该被索引的设计文档。
而且路径启发式本身失效 —— 大量 `main.py`、`__init__.py` 散在 `~/Documents` 下，
根本不在任何"代码目录"里。

**采用的方案：按扩展名降级**。源码/配置进 `CODE_EXTS`，只登记元数据不解析正文。

| | 改前 | 改后 |
|---|---|---|
| 入库文件数 | 2503 | 2503（不变，仍可按文件名搜到） |
| 需解析正文 | 1092 | **128（-88%）** |

**用户损失**：无法全文搜索源码内容。但那本就该用 ripgrep / IDE 全局搜索，
不是文件管理器的职责。

**关键细节**：`.md` **不归入** CODE_EXTS。它既是文档格式又常驻代码库
（README、设计文档），按扩展名归文档类是对的；用路径判断会误杀。

# M5 决策记录：三路检索与删除路径

## contentless FTS5 不支持 DELETE

写来源移除功能时才暴露：SQLite 报
`cannot DELETE from contentless fts5 table`。

`content=''` 模式下 FTS5 不存正文副本，删一行需要原文才能算出要从
倒排索引里摘掉哪些词元 —— 而它手里没有。后果是**索引只能进不能出**：

| 场景 | 现象 |
|---|---|
| 移除来源 | 记录删了，搜索仍命中，点开报文件不存在 |
| 文件被删/改名 | 旧内容永久留在结果里 |
| 重新索引同一文件 | 旧分片没清掉，同段内容重复命中 |

实测两种解法：

```
content=''                        → DELETE ✗
content='', contentless_delete=1  → DELETE ✓
```

另一条路 `INSERT INTO t(t,rowid,text) VALUES('delete',...)` 要求提供
被删行原文，删除时原文往往已不存在，不可行。选 `contentless_delete=1`。

**这个缺陷只在写删除测试时才会暴露** —— M1~M4 全是"加文件"路径，一路都绿。

## 建表语句有两份

`schema.py` 与 `search.py` 各有一份 FTS5 定义，实际生效的是前者
（`init_db` 执行它）。给后者加 `contentless_delete=1` 等于没改，
排查时以为选项无效。已合并为单一来源。

## 分词切错词边界 → 加第三路兜底

jieba 把「汝窑天青釉」切成 `汝窑天 / 青釉`。查「汝窑」时：

- jieba 路：索引里没有「汝窑」词元 → 0 命中
- trigram 路：「汝窑」2 字，短于 3 字符组 → 0 命中

两路同时失效。这不是换分词器或调参能解决的 ——
任何统计分词器都会在未登录词上切错，trigram 的 3 字符是其定义。

加第三路 LIKE 子串兜底，**仅在前两路召回不足（< 3 片）时触发**，
正常查询代价为零。不用"全空才补"是因为分词切错时前两路可能命中少量
其他分片，正确结果仍然出不来。

实测 8/8 命中且无假阳性（不存在的词仍返回 0）。

## 标题文字不在索引里

标题只存 `chunks.section_path`，不在 `text` 里 ——
「宋代五大名窑」作为 h1 标题时完全搜不到。
用户搜自己文档的标题却没结果，是最刺眼的一类检索盲区。
`index_chunk` 改为把 `section_path` 一起写入两个 FTS5 索引。

## SESSION_TOKEN 用 pop 导致重载后失效

`os.environ.pop("ORDO_TOKEN")` 会删掉环境变量，
模块重载时读不到，测试里第二个用例起全部 401。改用 `get`。
真正的隔离靠"不把令牌写进日志与响应"，不是靠删环境变量。

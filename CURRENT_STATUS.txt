Ordo 项目当前状态总结

一、项目定位

Ordo 是一个本地优先的个人知识库，目标是扫描固定磁盘中的资料文件，保留真实文件路径，并通过全文检索、语义检索和带引用问答帮助用户查找资料。

当前 Windows 来源模型已经统一为固定盘根目录：B:\、C:\、D:\ 等固定盘作为顶层来源，盘内的 openclaw、workspace、项目目录等不再创建独立来源，而是作为文件树节点逐层展开。文件仍然以真实路径登记，例如：

B:\openclaw\openclaw云端部署\workspace\notes.md

二、最终文件入库规则

当前确认的入库白名单为：

.txt
.docx
.pdf
.md
.csv
.html
.htm

上述七种格式都会解析正文，进入全文索引、语义向量和知识问答流程。

以下格式完全不入库：

.doc
.xlsx
.xls
.ppt
.pptx
图片、音视频、压缩包、电子书、设计文件、源码、配置文件、安装包、日志和临时文件。

白名单之外的历史文件在下一次对应固定盘扫描时会被标记为 ignored，从浏览、检索和问答中隐藏，但不会删除、移动、重命名或修改磁盘上的原始文件。

三、当前已经完成的功能

1. 固定盘来源发现

Windows 下来源发现返回固定盘根目录。微信、QQ、哈希目录和其他子目录不再作为顶层来源显示，真实目录结构通过左侧文件树展开。

2. 后台扫描

固定盘启用后，扫描在后台执行，任务阶段为：

scanning → indexing → embedding → done

如果 Ollama 或向量扩展不可用，任务状态会显示 blocked，不会把没有向量的状态伪装成完成。

3. 向量闭环

后台扫描完成后，会继续补齐当前扫描内容的向量。向量回填按批次提交，支持中断后继续，并记录 remaining、available 和 embedding 状态。

4. 统一可见性

停用来源、ignored 文件、已消失且没有保全副本的文件不会进入普通检索、向量检索、层级检索、重排、问答上下文和邻居扩展。共享内容存在多个副本时，问答会优先使用可见副本。

5. 元数据 SQL 路由

纯文件元数据问题直接使用 SQL 处理，不经过 embedding 或 RAG。例如文件数量、PDF 数量、来源文件数量、最近文件列表等问题可以直接返回结果。

6. 流式问答

新增 /ask/stream 流式问答协议，事件顺序为：

chat.searching
chat.draft
chat.regenerating（需要重新生成时）
chat.finalize
chat.citations

引用只在 finalize 之后发送。原有非流式 /ask 端点仍然保留，用于兼容和评测。

7. 增量索引

严格 200 片增量测试已经通过：修改 200 个分片中的 1 个分片时，只重新编码变化的分片，其他分片复用已有向量。

8. Windows runtime

源码模式 sidecar 已通过 Windows runtime acceptance：SQLite-vec 正常、Ollama bge-m3 正常、Cross-Encoder 运行时正常、搜索 smoke 有结果、没有 degraded 状态，sidecar 能正常退出。

Gold Evidence Recall@50 已达到 90% 门槛，压缩门槛也已经通过。
搜索 P95 与 Rerank P95 两条延迟门槛在 2026-08-18 的检索性能优化后已通过
（原为 4.1 秒 / 0.88 秒），详见 docs/RETRIEVAL-PERF.md。

延迟优化的三处根因（质量指标未变，逐位与优化前一致）：

1. 向量路每次查询都在 sqlite-vec 的 vec0 虚拟表上暴力 KNN 扫 71,378×1024 维，
   单路 782ms。改为进程内矩阵乘后 13ms。矩阵此前不可用是因为逐行导出全库
   向量要 369.7 秒；发现 vec0 实际把向量每 1024 条打包在影子表里，整块读
   70 个 blob 重建只需 1.1 秒（快 327 倍）。
2. 重排逐行从 vec0 取 80 个候选向量约 400ms，占 rerank 耗时绝大部分（打分
   本身只有几十毫秒）。改为从整库矩阵按 rowid 切片。
3. 620ms 的 Ollama 查询嵌入串在关键路径最前面，而它不依赖任何词法路线。
   改为后台线程与分层路由+词法四路重叠，并把所有查询变体合并成一次调用
   （实测一次调用编码 8 条也只要 719ms，成本几乎全是每请求固定开销）。

已用 ORDO_VECTOR_NO_MATRIX=1 强制走原 vec0 KNN 路径复跑评测，
两条路径的 Recall/MRR/nDCG 完全一致，确认只改执行方式、不改排序结果。

压缩评测结果（检索改动后复跑，全部通过；压缩延迟略有改善）：

但 nDCG 会掉到 88.5%，反而低于 local-static-v3，因此不采用。

生产默认保持 local-static-v3（交互搜索 P50 0.61 秒）；cascade 用
ORDO_RERANKER=cascade 开启。

关于 +15% 这条门槛本身：RRF 基线的 nDCG@10 已是 84.3%，+15% 意味着绝对值
要达到 97.0%。53 道题单文档相关，rank 1 得 1.0、rank 2 得 0.631，所以 97.0%
等价于「约 49 题排第 1、其余 4 题排第 2、且没有一题更差」，接近完美排序。
而且一级召回越强、分母越高、相对门槛越难达到（本轮 RRF 基线自身从 83.9%
升到 84.3%，把 nDCG 门槛从 96.4% 顶到 97.0%）。继续靠这 53 题调参逼近
97.0% 会违反 HANDOFF H12 的立意（评测集先于实现冻结、不因算法结果反向
修改）。建议由项目决定：改用绝对值口径，或先扩评测集再继续调 Rerank。

十、真实使用反馈的两条缺陷（2026-08-18，已处理）

反馈一：「有很多没用的 .md 文件在干扰」

  确认成立。真实库可见文件 6,266 个，.md 占 2,552 个（41%），集中在少数
  目录，文件名高度重复（readme.md 348、skill.md 265）。根因是入库白名单按
  扩展名过滤，而 .md 同时是你笔记的格式和每个代码仓库 / AI agent 配置的格式。

  顺带修掉一个真 bug：你家目录 C:\Users\guica 下有一个 .git，导致
  _looks_like_code_project 对家目录返回 True，家目录以下所有文件（OneDrive、
  WPSDrive、Desktop）都被判成"在代码项目内"。这是"打开整盘剪枝会误删个人
  简历和证件"的真正原因。现已修正：家目录与盘根永远不算代码项目。

  已生效的处理：按文件名分两层挡样板 —— agent 机器配置（skill / agents /
  claude / gemini 等）任何位置无条件挡；仓库样板（readme / changelog /
  contributing 等）只在代码项目内挡。实测清理 845 个，误伤 0
  （readme笔记.md 这类带中文后缀的会保留）。

  没有采用的两条自动方案（都会误删真资料，详见 docs/CORPUS-NOISE.md）：
  整盘剪代码项目会删掉你写在带代码标记目录里的「Agent面试题分类整理」和
  「SimOS/实现路线图」；按 docs/ 目录名排除会删掉你自己项目的设计文档 ——
  InkHole/docs 下的「墨洞项目计划」正是 gold 评测 X07 题依赖的资料。

  剩余噪声（openclaw / TradingAgents 的 docs 等约 1,700 个）改为交给你决定，
  新增按目录排除机制：

    cd services/api
    .venv/Scripts/python.exe scripts/exclude_dirs.py --list
    .venv/Scripts/python.exe scripts/exclude_dirs.py --add "B:/openclaw"

  排除只作用于索引层：不移动、不改名、不删除磁盘上任何文件，记录保留
  （置 ignored），取消排除后恢复。桌面端 UI 尚未接入，目前走命令行或 API。

反馈二：「回答的内容好少」

  确认成立，且根因不是预算（上下文 64,000 字符 / 120 分片，
  answer_max_tokens=auto 不传上限），而是提示词写着"通常用 1 至 6 个简短
  条目"。那是为把引用支持率做高而优化的写法 —— 每行一个可验证事实最安全，
  代价是读起来单薄。提示词在按指标优化，而不是按体感。

  已改为：覆盖资料中直接回答问题的全部事实（通常 3 至 12 行，证据充分可
  更多），每行写成完整的一句话、把相伴的数值与限定条件写进同一句。
  一条安全约束都没放松（仍不加背景知识与推理、每行带引用、无依据只拒答）。

  **待办（重要）：该改动尚未用 65 题 QA 复验。** 2026-08-18 尝试复验时
  cc-switch 里 7 个配好的 provider 全部不可用（myself / modelshare 返回
  HTTP 503，kocode / Z30 / ModelShare / 佬友炸弹车 返回 403，anyrouter 超时），
  属外部阻塞。

  因此必须注意：第九节记录的引用支持率 96.99% 等门槛数字，是用**旧提示词**
  测出来的，当前代码的提示词已经不同。在复验通过之前，不应把那组数字当作
  当前代码的门槛结果。

  风险性质：引用的**强制执行在代码里，不在提示词里**（H8「prompt 是建议，
  校验是执行」）。四条后置硬校验（虚构引用剔除 → 零引用重生成 → 降级为检索
  结果 → 拒答句夹带事实则截断）一行未动，且已验证新提示词仍禁止背景知识与
  推理、仍要求每行带引用、仍保留拒答规则。所以放长回答的风险是**指标可能
  下滑**，不是安全性下滑。

  provider 恢复后的复验命令与判据见 docs/CORPUS-NOISE.md 第 4 节末尾。
  任一门槛跌破就把提示词改回原来的「1 至 6 个简短条目」——
  不为"回答长一点"牺牲引用可靠性。
